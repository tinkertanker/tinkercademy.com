The Android team and community advocates testing. This includes unit, integration, and UI testing.

{/* medium-image:1*xQRZhzYbKvU8VfMDnyhWQQ.png alt-decision:meaningful */}

![“One does not simply test in production” meme](/blog-media/a9e6d72f9862647cda265bb2f013a68018b0cb211dc5d89a6cbf0711bbff5fe8.png)

I’ll focus on <strong>UI testing</strong> for this post.

Testing brings about several benefits to the app development process:

1. Acts as a specification for the app’s behaviour
2. Verifies that the app behaves according to the specification
3. Gives confidence that any changes made during development do not break existing functionality

The last point is especially important to apps undergoing major refactors and redesigns. <a href="https://play.google.com/store/apps/details?id=com.tinkertanker.tanjinyi.androidmicrobitcms">Get Hacking Android</a> is no exception.

## The Initial State of Get Hacking Android

> <a href="https://play.google.com/store/apps/details?id=com.tinkertanker.tanjinyi.androidmicrobitcms">Get Hacking - Digital Maker - Apps on Google Play</a>

Get Hacking Android is an app that showcases <a href="https://microbit.org/">micro:bit</a> and maker projects. Tinkertanker released a first version over a year ago on the Play Store, but without any UI tests for the app. This meant that functionality could break during development without anyone noticing. (Unfortunately, some of these bugs <em>did</em> actually slip into production.)

The app is also undergoing a major redesign, and this impacts many areas of the code base. Breakages are likely to happen.

Writing UI tests can help avoid these issues. I’ve written some and documented what I’ve learnt below. This includes some of the patterns I’ve followed and the pitfalls I’ve encountered.

## Preparing to Test

Before writing any tests, I set up the dependencies needed for testing. These include the Espresso and AndroidX Test libraries.

### What Is Espresso?

<a href="https://developer.android.com/training/testing/espresso">Espresso</a> is a UI testing library for Android. It provides APIs for writing idiomatic actions and assertions on the UI.

Tests written with Espresso are concise and readable.

### What Is AndroidX Test?

<a href="https://developer.android.com/training/testing/set-up-project">AndroidX Test</a> is a set of libraries to ease testing on Android. It provides test harnesses and utilities that make writing tests simpler.

{/* medium-image:1*yfho5jJ7_G5Kgqw2H0YD5w.png alt-decision:meaningful */}

![The logo for AndroidX Test](/blog-media/380a30ba3204268ea0e85e953a404a80d4bbe4c400c8493ee5cc23ac099001b0.png)

<em>The logo for AndroidX Test</em>

The <a href="https://junit.org/junit4/">JUnit</a> and <a href="https://google.github.io/truth/">Truth</a> extensions provide methods for fluent assertions. These exist under the <code>androidx.test.ext</code> namespace.

<a href="https://developer.android.com/training/testing/junit-runner">AndroidJUnitRunner</a> makes it possible to run JUnit-style tests on Android devices. It exists under the <code>androidx.test:runner</code> namespace.

<a href="https://developer.android.com/training/testing/junit-runner#using-android-test-orchestrator">Android Test Orchestrator</a> enhances test reliability by running tests in separate <a href="https://developer.android.com/reference/android/app/Instrumentation.html">Instrumentation</a> instances. Some of my tests were flaky and failed without it. It exists under the <code>androidx.test:orchestrator</code> namespace.

## Understanding the Android Test File Structure

There are a few common rules to writing UI tests:

- Store all on-device UI tests in the <code>androidTest</code> directory.
- Store each test class in the same subdirectory under <code>androidTest</code> as the class under test.
- Give each test class the same name as the class under test, but suffixed with the word <strong>Test</strong>.

> Side note: Store off-device UI and unit tests in the <code>test</code> directory instead.

Here’s an example.

I want to test an <strong>ExampleActivity</strong> class. I store it in <code>app/src/main/java/com/example/example-app/ExampleActivity.java</code>.

In this case, I should name my test class <strong>ExampleActivityTest</strong>. I should also store it in <code>app/src/androidTest/java/com/example/example-app/ExampleActivityTest.java</code>.

## Writing My First Test Class

To get started, I first wrote a test class for a simple Activity in the app: IntroductionActivity.

There’s a bunch of different things going on at first glance. Let’s walk through each part in more detail.

### Using ActivityScenario and ActivityScenarioRule

<a href="https://developer.android.com/guide/components/activities/testing">ActivityScenario</a> is essential to testing Activities on Android. It manages the state and lifecycle events for the Activity under test. This eases Activity behaviour testing.

<a href="https://developer.android.com/reference/androidx/test/ext/junit/rules/ActivityScenarioRule">ActivityScenarioRule</a> builds upon ActivityScenario. It launches an ActivityScenario before each test and cleans up after each test.

For IntroductionActivityTest, I used ActivityScenarioRule to launch IntroductionActivity before each test.

The first test verifies that the app displays these two views:

<ArticleEmbed provider="github-gist" href={"https://gist.github.com/zwliew/c18c75d0c8d8dcc3de44d8322d70e6ac"} title={"IntroductionActivityTest.java"} />

I used Espresso APIs here. They may be unfamiliar if you haven’t written UI tests before, but the intent of the code should be clear.

### What Are These Methods?

The Android documentation provides <a href="https://developer.android.com/training/testing/espresso/basics">a detailed explanation</a> of common Espresso APIs. For convenience, I’ll give a quick introduction to each method I used.

<code>onView()</code> matches a View given one or more ViewMatchers objects.

<code>check()</code> checks the state of the matched View given one or more ViewAssertions objects.

<code>matches()</code> returns a ViewAssertion object that asserts on the given ViewMatcher objects.

<code>isDisplayed()</code>returns a ViewMatcher object that matches a displayed View.

### Naming Test Cases

I named each test case following a structured scheme. It goes like this: <strong>[action/condition]_[expected result]()</strong>.

This naming scheme tells readers the intent of a test case at a glance.

In onClickButton_showsMainActivity(), onClickButton is the action and showsMainActivity<strong> </strong>is the expected result.

### Structuring Code in Test Cases

The Android team recommends structuring test code based on <a href="https://en.wikipedia.org/wiki/Given-When-Then">Given-When-Then (GWT)</a>.

GWT splits code into three phases:

- Given: The initial state of the app.
- When: The action to carry out. This is like the action used in naming the test case.
- Then: The expected result. This is like the expected result used in naming the test case.

In onClickButton_showsMainActivity(), I separated the three parts with a newline.

There is no <strong>Given</strong> phase in the test.

<code>onView(...)</code> occurs during the <strong>When </strong>phase.

<code>intended(...)</code> occurs during the <strong>Then</strong> phase.

### Performing ViewActions

Espresso provides ViewActions that perform actions like clicks, typing, and scrolls on Views.

I used <code>perform(...)</code> and <code>click()</code> to click on the Button in IntroductionActivity.

### Verifying Intents

To verify that the app launches the correct Intent when clicking the Button, the test has to do two things:

1. Capture the launched Intent
2. Check that the Intent has the MainActivity as the component

First, I used the <a href="https://developer.android.com/training/testing/espresso/intents">Espresso-Intents</a> extension to capture Intents. It lives in the <code>androidx.test.espresso:espresso-intents</code> dependency.

<ArticleEmbed provider="github-gist" href={"https://gist.github.com/zwliew/93fb07bbb00fd8f73a0b67a9ec57ed48"} title={"IntroductionActivityTest.java"} />

I set up pre-test and post-test hooks using the <a href="http://junit.sourceforge.net/javadoc/org/junit/Before.html">Before</a> and <a href="http://junit.sourceforge.net/javadoc/org/junit/After.html">After</a> JUnit annotations.

The pre-test hook initialises the Intent captor to capture launched Intents.

The post-test hook releases the Intent captor for garbage collection.

> Note: An <a href="https://developer.android.com/reference/android/support/test/espresso/intent/rule/IntentsTestRule">IntentsTestRule</a> can automate initialisation and release for each test.

> But IntentsTestRule also launches the Activity under test. This conflicts with the ActivityScenarioRule that I’ve set up.

Next, I used the <code>intended()</code> and <code>hasComponent()</code> methods to verify the captured Intent.

## What’s Next?

I’ve walked through the process of writing my first UI test class for Get Hacking Android. I’ve documented common patterns like test naming schemes and file structure. I’ve introduced Espresso APIs used for handling Activities, Intents, and Views.

But that isn’t all.

Get Hacking Android uses <a href="https://developer.android.com/reference/android/support/v4/app/Fragment.html">Fragments</a> for navigating between pages. It also performs network operations with <a href="https://square.github.io/retrofit/">Retrofit</a> to fetch data from a backend.

Possibly in another article, I’ll explain testing Fragments with <a href="https://developer.android.com/reference/android/support/v4/app/FragmentTransaction.html">FragmentTransactions</a> within ActivityScenarios. I’ll also explain waiting on network operations with <a href="https://developer.android.com/training/testing/espresso/idling-resource">Espresso idling resources</a>.

> Note: I used FragmentTransactions instead of the new <a href="https://developer.android.com/training/basics/fragments/testing">FragmentScenario</a> API. This is because Get Hacking Android has yet to migrate to AndroidX Fragments.

> If you use AndroidX Fragments, you should check out FragmentScenarios instead.

I may also explain testing authentication and user inputs using <a href="https://android-developers.googleblog.com/2015/12/leveraging-product-flavors-in-android.html">different product flavours</a>.
